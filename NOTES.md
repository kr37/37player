# 37 Player: notes

The big picture as of 31 October 2026 (version 1.4.148). Commit messages hold the detail of each change. This file says how the whole thing works and why it is the way it is. Update it when a decision changes.

## What it is

A playlist player for live sessions at Kadampa centers: chanting, prayers, mandala offerings, teachings, with silences and stops between them. It's built for an operator who needs the right audio, in the right order, every time, often on an old computer or an iPad. It came out of IKRC's old and new Macs being unable to share a Music.app library, and Music.app becoming hard for non-technical people to use.

- One self-contained HTML file, `37-player.html`, running as a PWA. It's offline-capable, and the whole library (audio included) lives in the browser's IndexedDB.
- Users so far: Gen Rinzin, two friends, and Samudrabadra (Fort Myers). Prospective: KMC Texas (three rooms wanting one shared library) and IKRC (Macs and an iPad). Phones are a "handy sometimes" platform, not the main target.

## Architecture in brief

- **IndexedDB `temple-sound-library`.** Never rename it, or every user loses their library. Stores: `state`, `audio`, `artwork`. Audio and artwork are keyed by track ID; IDs never change.
- **The storage layer** (1.4.151, the first step of v2). Nothing outside it touches IndexedDB: a library's storage is a *library store* with one small interface, `get`, `put`, `del` (one key or several, all or none), `keys` (optionally by prefix), `update` (read some records and write or delete in one step, as for the copies waiting in `incomingCopies`), `clear` / `pruneExcept` (keeping `STATE_KEPT_ON_CLEAR`: backup, converter, libraryInfo), `writeRootIfCurrent` (the library record, only if its revision is unchanged) and `close`. Today's one implementation is `IdbLibraryStore` (reconnecting when the browser closed the connection, `settleTx` resolving only once a write is really done). This window's library is `libStore`; another library's is `storageOpen(id)`; the device's are `storageLibraryIds()` and `storageRemove(id)`. The app's own rules stay above it, in `idbPut`, `idbDelete` and the rest (revisions, backups to redo, a library that didn't load). A second implementation (files on disk, then Tauri) only has to keep the same promises. **The files store** (1.4.152, step 2, `FolderLibraryStore`): the same promises kept with files. For now only in the browser's private file system (OPFS), chosen per device by localStorage `37player.storage` = `opfs` (nothing in the app offers it yet); a folder the person chooses, and then Tauri, come next. A library is a folder: `state/`, `audio/`, `artwork/`, one `<key>.json` per record, its files (blobs) beside it as `<key>.<tag>.<ext>` and in the .json as `{"$blob": name, type, size}`; keys keep a–z 0–9 _ -, anything else (capitals too: Windows and Mac folders ignore case) is %XXXX. **Every write gives a file a new name** and the replaced or deleted one waits a day in `orphans.json` (`FILES_GRACE_MS`) before it's removed: a browser can't read a file that changed after it was opened (IndexedDB kept the old copy alive as long as it was in use, so a track playing while its audio was replaced or deleted carried on), and this keeps that. Files first, the .json last, so an interruption leaves the record as it was; leftovers are found by the tidy run 20 s after opening. One writer at a time per library across windows (Web Locks), reads unlocked (each .json is swapped in whole). Tests: tests/filestore.js; and any test runs on the files store with `STORE=opfs` when the test copy is made (make-debug-copy.py): bkkeep, undo, copylib, share, p37, stopimport, dlcrash, miss, part, fold, rev, dup all OK that way (tests that open IndexedDB themselves can't). **Libraries in a folder the person chose** (1.4.153, Chrome/Edge on a computer; Gen Rinzin's option C, 4 Nov 2026: the closest a browser gets to Move and manage, and down from three copies to two). Settings → Library info → **Kept in** → **Keep it in a folder…** (`moveLibraryToFolder`): explains (where, about how much, automatic backups stop), the person picks a place (`showDirectoryPicker`, starting in Music), 37 Player makes a folder named after the library there (or, 1.4.180, Gen Rinzin: with several libraries he made an empty folder for this one first and got `Name/Name`, so a folder that is this library's, or empty and named like it, is used as it is, and another empty folder asks "Use “X”" or "Make “Name” inside", the latter suggested when X looks like a holder such as "37 Player Libraries" or Music) with `37 Player library.json` (`FOLDER_MARKER`: format, library ID, name) and a README, copies audio and artwork, then the state records last, while holding the sync, transfer, backup, standardize and incoming locks; checks every key arrived and the library record's revision didn't move; then marks the library list entry `folder` (the folder's name), keeps the folder's handle in its own tiny database `37player-folders` (browsers remember folders only as handles in IndexedDB; lose it and the person points at the folder again), tells other windows (`moved`: they stop and reload) and reloads. A stopped or failed copy leaves the browser's library as it was; choosing the same place again carries on. After the reload, `offerRemoveBrowserCopy` offers to delete the IndexedDB copy (Remove the browser's copy / Not now). `storageOpen` gives a folder library a FolderLibraryStore on `libraryFolderDir(id)`, which checks permission and the marker. **Start:** `ensureLibraryFolder` before anything is read: no permission → "Open it" (asks); folder gone or note lost → **Find the folder…** (refuses a folder whose marker isn't this library's); or **Open another library**. An installed app keeps the permission; a tab may ask after a restart. **Backups:** a folder library is its own safe copy (Gen Rinzin: no continuous backups in v2): `autoBackupActive` and `libraryNeedsBackup` are false, `libraryProtected` true, the backup button reads **In a folder** (tooltip: back it up with the computer, or export a .37p; clicking still offers a manual backup). **Deleting** such a library forgets it; the folder and its files stay, and the dialog says so. Not yet: readable artist/album names; the 24-hour Deleted folder; a Move that removes originals. Test: tests/folderlib.js (stand-in folders in OPFS). No change in behaviour: 17 tests run (libs, copylib, undo, full, quota, notloaded, libdel, bkkeep, restore, e2e, dlcrash, pieces, damaged, share, p37, stopimport).
- **Readable recording names** (1.4.174; v2, Gen Rinzin: integral, the same week as leaving IndexedDB). In a library kept as files (Chrome/Edge folder libraries, the OPFS test store, later the desktop app), recordings are `music/<Artist>/<Album>/<NN> <Title>.<ext>` (under `music/` since 1.4.179, Gen Rinzin: the folder's top reads like a table of contents, and it matches the portable export), named as the portable export names them (`recordingPathFor`, `recordingPathPart`: `Unknown Artist` / `Unknown Album`, what Windows and the Mac refuse becomes "-", device names get "_", parts kept to 80 characters); a clash gets " (2)". Everything else is in `37 Player's own files/` (a library made before keeps `state/`, `audio/`, `artwork/` at its top, and only its recordings move out). The audio record points at its recording by `{"$path": …}`. `renameRecordings` runs 2.5 s after each save (`scheduleRecordingRenames`) and once after opening: a recording whose details changed is moved (so Undo moves it back); one a player holds is copied and the old file waits its day (`canMove`, `trackHeldByAPlayer`); a change of capitals only is left alone, since Windows and Mac folders ignore case and the old name would be tidied away. Readable files go on the waiting list before they're written, so tidying removes one an interrupted write left, but never a file 37 Player didn't write; emptied album and artist folders go too. Re-tagging writes over the recording's own file (same name): a player holding it at that moment may stop. The folder's README says what's where (kept current, `keepFiles("readme")`). **`playlists/`** (1.4.179, Gen Rinzin): an .m3u8 for each playlist, in its folders, pointing into `../music/`, written as the portable export writes them (`buildPlaylistEntries`), tracks only (silences and stops left out); a courtesy for other players, never read by 37 Player; kept in step after each change (`syncPlaylistFiles` → `FolderLibraryStore.keepFiles`, which rewrites only what changed and removes only files it wrote itself, remembered in `37 Player's own files/written.json`). Only the app's own library gets names (`storageOpen` for `LIBRARY_ID`, the move into a folder); IndexedDB is unchanged. Tests: readnames.js (the store), folderlib.js (moving in, renaming on an edit).
- **Several libraries on one device** (1.4.001; Settings → Switch libraries, and the name in the top bar once there's more than one). Each library is its own database: the first is `temple-sound-library` (id `main`), the others `temple-sound-library~<id>`. The list is in localStorage `37player.libraries` (names, sizes, the last one chosen, ids of deleted ones), and each database also holds its own name (state record `libraryInfo`) so a lost list is rebuilt from `indexedDB.databases()` (`rediscoverLibraries`).
  - **Switching reloads the page** into the other library (`switchLibrary`), so nothing in memory carries over. Which library a window has open is per window (sessionStorage `37player.library`); two windows can have two libraries open.
  - **Per library:** everything in its database (library, view settings, session, backup record and folder, `sharedBase`, `sharedPending`, `sharedSeen`), and the channels, locks and localStorage keys that concern its contents: `libScoped()` adds `~<id>` (`37player-sync`, the sync, transfer, backup, tag-snapshot, mp4-repair and standardize locks, `37player.analyzing`, `37player.sharedLog`). The first library keeps the old names, so an older window still agrees with a newer one.
  - **Per device:** `DEVICE_SETTING_KEYS` (language, display, screen-off playback, the default device name, server addresses) in localStorage `37player.device`, laid over each library's settings on load and saved with every save; a `storage` event brings another window's change in before this window can save the old value back. The converter stays in the first library's database whichever is open (`mainStateGet/Put/Delete`). Device-wide channels and locks: `37player-playing`, `37player-version`, `37player-convert`, `37player-converter-fetch`, and `37player-libraries` (the list changed; a library was deleted).
  - **Only the open library syncs.** A new library starts empty (the starter prayer is only for the first). New library → Join a shared library joins at once after the reload (sessionStorage `37player.pendingJoin`) and takes the shared library's name. Joining from a library that already has tracks offers a new library first, since combining would put them in front of everyone.
  - **Deleting** is for libraries that aren't open: their database is deleted (the first library's is emptied instead, as it holds the converter). Windows on it are told, close it at once, and reload into another.
- **State is split** into the library (`library`, `tree`, `rev`) and the view (settings, session). The library is written only when its hash changes, and only if no other window has written since (`idbWriteLibraryIfCurrent`). A BroadcastChannel keeps other windows live.
- **Old windows:** two windows on one computer share one library, so a window left open on an old version syncs by old rules (a 1.3.021 window and a 1.3.045 one re-saved the library every 3 minutes all night). Each window announces its version on BroadcastChannel `37player-version`; one that hears of a newer version stops syncing and asks to be reloaded (1.3.047). Devices also strip local-only fields (`SYNC_LOCAL_TRACK_FIELDS`) from the shared library as they receive it (1.3.046).
- **Rule for all code:** `root.library` and `root.tree` can be replaced at any moment by another window or a sync. Hold IDs, never long-lived object references.
- **`sw.js`** can't be inlined (a spec restriction). It caches only the app page and `help.json`, network-first, and skips Range requests.
- **Help** is Markdown in `help/NNN Title.md`. It's embedded into the HTML because a `file://` copy can't fetch `help.json`. It's English only, by design.
- **The UI** is translated into 9 languages (en, es, fr, pt, de, zh, vi, el, it). Every new string goes into all nine.

## Playback model

- **Highlighted vs. queued.** "Highlighted" (`selectedItemId`) is UI only. "Queued or playing" (`currentItemId`) changes only through `activateItem()`. A single click highlights; a double-click or Enter plays from the start.
- **Each step.** The next item is looked up fresh when an item ends, so edits made mid-session take effect. Deleting the playing entry lets it finish.
- **Silences and stops.** Silences tick on their own clock. Stops wait for a click.
- **Only the latest press counts.** If a track's audio must be fetched first (shared library), a press that's still waiting is dropped when another is made. Playback never starts by itself minutes later.
- **Loudness.** "Even out loudness" and per-track +/- adjustments use `el.volume` when turning down. Turning up needs Web Audio (`createMediaElementSource` into a GainNode). Once an element is routed that way, it stays routed until reload.
- **No peak limit** (1.4.098, `trackLevel`; before, 1.4.059, evening out stopped at the loudest peak). Evening out and a track's own boost (✎, `volumeDb`) both go past the peak if that's what it takes; the details say how far past full volume the peaks go (`over`) and that turning the track down by as much avoids the distortion. Gen Rinzin: loud enough on small speakers, with a warning, beats too quiet. Album by album is the default kind (`levelKind`, Settings lists it first). Album mode is one gain per album, an album being its name and artist since 1.4.131 (its combined loudness), and each track's own Volume is added on top in either mode, and also with evening out off.

- **A silence's clock on a computer** (1.4.158; SKBC's Mac mini, the desktop app, 5 Nov 2026: a 60-second silence took 60–69 s with the window covered, 69 s hidden; Gen Rinzin's stopwatch). A silence's time is real time (`advanceSilence`), but it was only looked at on animation frames and the silent loop's `timeupdate`, which a covered or hidden window on a Mac gets rarely; tracks moved on on time, because a recording's `ended` still comes promptly. Now, except on touch screens (phones and tablets keep their tested arrangement), a silence also plays a silent WAV exactly as long as the time left, in pieces of up to 30 s (`runSilenceClock`, `silentWavBlob`: 8 kHz, 8-bit), and each piece's `ended` looks at the clock. Gen Rinzin's earlier tests on other computers may not have caught a few seconds a minute either. Test: tests/silclock.js (no animation frames or timeupdates from page load; fails on 1.4.157).

### Playing with the screen off (phones and iPads)

The hardest-won part. Found and fixed in October 2026 (1.3.022 to 1.3.028), using the playback log.

- **The problem:** on Android and iPadOS, a track that starts while the app is off screen (screen locked, or another app in front) plays for a couple of seconds, then goes silent. The player still reports "playing" and its time keeps running. The sound comes back when the app returns to the screen.
- **The fix:** while the app is off screen and the player is playing, a silent 10-second WAV loops on its own `<audio>` element (`silentKeepAlive`, `updateLoopHold`). The page never stops making sound in the phone's eyes. The same loop already carried silences along with the screen off.
- **Between items** (`playBridge`): the moment after one item ends and before the next is really playing counts as still playing. The loop stays on and the lock screen keeps saying "playing".
- **Stops** (`stopHold`): with "Keep the lock screen ready at stops" on (default), the silent loop runs through a stop, the lock screen shows the stop's name, and its play (or pause) button continues the session. Off saves battery; then a stop needs 37 Player itself.
- **Pauses off screen** (`pauseHold`, same setting, now "…at stops and pauses"): after a pause with the app off screen, the silent loop runs for up to 30 minutes so the lock screen's play still works. Without it an iPad put the page to sleep at once, and play gave no sound.
- **Lock-screen commands:** Media Session "play" only plays and "pause" only pauses. They used to toggle, so a stray "play" from the phone paused a playing track.
- **Phone pauses at a track's start:** if the phone pauses a track within 5 seconds of its start, with the app off screen and no press, it's restarted once. Later pauses (a phone call, unplugged headphones) are respected.
- **Diagnosis:** the **playback log** (Settings → Playback, `playLog()`) records track starts, the app leaving and returning to the screen, pauses the phone made, and a "still playing" line every minute. Keep it. Ask for it first whenever playback misbehaves on a device.

## Shared library sync (1.3.000 onward)

The full plan and history are in the project doc `shared-library-sync.md`. In short:

- **Server:** `sync.php` is plain PHP, with no framework or database. Libraries are joined by a secret code; the server stores only its hash.
- **Versions:** each library version is one JSON file, so history comes free. Saves are "only if still at version N" (`flock`); otherwise the server returns 409 and the app merges and retries. Audio and artwork are named `id.rev` and never overwritten.
- **Merging** is three-way: this device, the shared library, and the last-agreed base (IndexedDB `sharedBase`).
  - A change made in one place wins.
  - A track changed in both places merges field by field.
  - A playlist changed in both places: both are kept, with the device name added to the copy and a ⚠ mark.
  - Edited on one device, deleted on another: the edit wins.
  - A sibling merely moving is not an edit, so it never revives a deletion.
- **Engine:** the merge engine is the `SYNC-MERGE:BEGIN/END` block, pure functions with their own tests.
- **Transfers:**
  - Audio moves in the background, one window at a time: `navigator.locks`, with separate locks for down and up.
  - It waits while anything plays, because transfers made phones crackle. A track you press play on is still fetched at once, with one download per file at a time.
- **Keep syncing with the screen off** (phones and tablets): a setting that stays as set (`cfg.keepAwake`). While on, whenever there's something to send or receive and nothing is playing, a silent loop keeps the page awake, with progress on the lock screen. Playback stops it; it restarts the moment playback stops. The lock screen's pause holds it off until the app is next on screen or plays. When a track is paused part-way, the lock screen keeps the track ("Paused · Receiving 2 of 5"), and its play (or pause) button resumes the track.
- **Review changes:** a FreeFileSync-style overlay with arrows per row (send / take / skip). It holds back automatic syncing while open.
- **What's on this device** (1.4.007, `openSharedChoose`): the whole shared library as a tree with checkboxes and sizes; Albums open (▸) into their tracks, each ticked on its own with its size (1.4.068; ticked, a track comes with no playlist, which the selection already allowed: it's the set of folders, playlists and loose tracks); a track that comes with a ticked playlist shows ticked and locked, "comes with a playlist". Apply (`sharedApplySelection`) builds this device's document without what was unticked, marks what was ticked "take", and runs the review steps (`syncReviewRows`, `syncClassifyPartial`, `syncApplyDependencies`, `syncApplyReview`), so the engine is unchanged. On a full-sync device, unticking switches it to partial first, after asking. Settings → Shared library: **On this device: Everything / Only what I choose** replaces the Partial sync switch; with Only what I choose, **New playlists from other devices come here by themselves** (`cfg.autoNew`: before an ordinary sync, `sharedBringNewOnes` ticks what's new since last looked, by `sharedSeen`; turning it on marks everything current as seen). Opening What's on this device marks what's new as seen too (1.4.062: the count goes, the New marks stay for that visit), unless `cfg.autoNew` is on; before, only Apply did, and Apply needs a change, so "2 new" couldn't be dismissed. The New marks are bright green and beside the name (1.4.063): the small amber ones went unnoticed. Review changes is now only for Review mode; the "new" badge opens What's on this device.
- **Partial sync** (a "left sync", "Only what I choose" in the app):
  - **What it means, since this keeps being forgotten:** a LEFT JOIN with this device on the left. Everything on the device is also in the shared library; the shared library may hold more that this device doesn't. So once a partial-sync device is up to date, the shared library already has every one of its files, exactly as with a full-sync device. "Partial" only ever means the device holds less, never that the shared library does. Nothing on a partial device is device-only (that would be the old "On this device only" folder idea, never built).
  - Everything on the device syncs both ways.
  - New playlists from others arrive only when chosen in Review.
  - New tracks in playlists the device already holds arrive automatically.
  - Deleting offers three choices: Cancel / Remove from this device / Delete everywhere.
- **Missing tracks** are marked big and clear, saying where each one is coming from ("on its way from {device}" or "waiting for {device} to send it").
- **Upload size limit:** Apache 2.4.54+ refuses request bodies over 1 GiB by default (`LimitRequestBody`), answering 413. A 1.2 GB WAV hit it. Both sites' vhosts on the droplet have `LimitRequestBody 0` (confirmed 29 Oct 2026; see SYNC-SETUP.md). The app now stops resending a refused file until "Sync now" and says so in the status (1.3.045). A later improvement: send big files in pieces (resumable).
- **Mobile data:** treated like any other connection, because library integrity matters more. Only the join dialog warns about the size.

## Non-obvious decisions

- **A backup folder never loses a file for a track that's still in the library** (1.4.150, `runFolderBackupHere`, `backupFileFor`). Before, a track went on the backup's keep list only if its audio was in IndexedDB at that moment, and every other file in `audio/` and `artwork/` was deleted, while meta.json still listed the track. So a full disk, a restore whose writes failed, or storage the browser threw away while the track list came back from the shared library made each backup empty the folder of exactly what it was there to keep. That fits Gen Rinzin's T470 (1 Nov 2026): the backup's library had 2,587 tracks and audio for 1. Now a track with no audio (or artwork) here keeps the folder's file and its `audioRevs` entry; only a track leaving the library frees its file. The playback log says how many were kept. Test: tests/bkkeep.js (fails on 1.4.149).
- **Colours and controls** (1.4.149; designed with ChatGPT on 2–3 Nov 2026 in the `chat` branch, 1.4.148.1–12, merged and tidied by Claude). ## Browser quirks and workarounds

**Ways to run it, and what they really are** (6 Nov 2026, Gen Rinzin worried quirks get lost). Eight ways (with Android), but three engines, two places for the library, and a shell or not. Quirks belong to the engine or the storage, so code tests for what a browser *can do* (`window.showDirectoryPicker`, `WEBKIT_ENGINE`, `IN_DESKTOP_APP`), never for a device's name, and each quirk is written below under its engine.

| Way | Engine | The library is in | Notes |
|---|---|---|---|
| iPad, on the Home Screen | WebKit | browser storage | first-class; no folders; touch |
| iPad, in a Safari tab | WebKit | browser storage | Safari may erase it after 7 days unused (37 Player warns) |
| Firefox, Safari on a computer | Gecko, WebKit | browser storage | works; no folders, no automatic backups |
| Chrome, Edge, Brave on a computer | Chromium | browser storage, or a folder (readable names) | first-class; Brave needs its File System Access flag |
| Desktop app, Mac | WebKit (the system's: Monterey's has no SIMD) | browser storage; a folder from bridge 2 | first-class |
| Desktop app, Windows | Chromium (WebView2) | browser storage; a folder from bridge 2 | first-class |
| Linux | Chromium (Chrome's installed app) | as Chrome | the desktop app on Linux would be WebKitGTK (playback through GStreamer plugins); not built |
| Android tablets and phones | Chromium (Chrome) | browser storage | no folders on Android; touch, as the iPad |

**WebKit, everywhere it runs** (Safari, iPads, the Mac desktop app; WebKitGTK too):
- IndexedDB stores a blob that is a slice of another, or made from slices, as the start of the whole original: re-tagged files (1.4.016, `putRewrittenAudio`), and tracks of an imported .zip (1.4.173, `webkitOwnBytes`). Anything stored there gets bytes of its own first.
- No WebAssembly SIMD before Safari 16.4, and the Mac desktop app on Monterey always has the old engine: the converter is built without SIMD (1.4.166).
- Timers in a hidden or covered window run late, so silences are timed by a silent audio clock (`runSilenceClock`, 1.4.158).
- No folder access (`showDirectoryPicker`) at all.

- **Clear a file input's value only after copying its files.** Chromium 141 empties the input's FileList in place when its value is cleared. Copy with `Array.from()` first.
- **Playlist files report as audio.** `.m3u8` reports as `audio/x-mpegurl`, so audio is picked by extension, never by MIME type.
- **Safari:**
  - it clears a site's data after 7 days without use, unless the app is on the Home Screen or Dock;
  - it uses dynamic viewport (`dvh`) heights;
  - the window's scroll position needs resetting, except while typing.
- **iPad touch:**
  - no hover, so row icons appear on selection;
  - drag and drop is synthesized from touch for the folder tree;
  - native `draggable` is turned off on coarse pointers.
- **Folder access:** `showDirectoryPicker` works only in Chrome and Edge on desktop. Brave needs `brave://flags` → File System Access. iOS Chrome is WebKit, so it has no folder access either.
- **Codecs:**
  - ALAC and WMA play in no browser, so they're converted with the scripts in `scripts/`.
  - What MediaRecorder writes as "AAC" varies by browser. Some write Opus, which `findMp4AudioCodecFourcc` catches.
- **Long recordings and memory:** decoding a whole file holds it all as raw samples (a 2-hour stereo teaching is about 2.5 GB), which crashed a phone's tab ("Aw, Snap!") and made a laptop give up with a flat stand-in waveform. Past a per-device budget, MP3s are decoded about 3 minutes at a time, cut at frame boundaries (`analyzeMp3InPieces`), and WAVs are read a few MB at a time with no decoder (`analyzeWavInPieces`); both feed `makePieceAnalyzer` / `makeLoudnessMeter`. Since 1.4.108, AAC in an .m4a/.mp4 too (`analyzeM4aInPieces`; Gen Rinzin's long Zoom recordings had stand-ins and no loudness): `m4aAacFrames` reads the sample table (stsz, stsc, stco/co64) and the AudioSpecificConfig (esds), and about 3 minutes of frames at a time (45 s on a phone) each get a 7-byte ADTS header and go to `decodeAudioData` as plain .aac. Each piece after the first starts one frame early and drops that frame's sound (AAC overlaps frames); the edit list's lead-in (`elst` media_time) and its duration are honoured, so the result matches decoding the whole file exactly (tests/m4apieces.js). Apple Lossless and other non-AAC throw, keeping the stand-in; on phones an .m4a still decodes whole when it fits (it may be Apple Lossless, which Safari decodes but can't be cut this way). Since 1.4.114 also FLAC (`analyzeFlacInPieces`: a minimal header from STREAMINFO, total and MD5 left unknown, then frames; cut where a frame starts, found by sync code and header CRC-8), Ogg Vorbis and Opus (`analyzeOggInPieces`: the header pages, then whole pages starting with one that doesn't continue a packet), WebM/Matroska (`analyzeMkvInPieces`: EBML header and the Segment's children up to the first Cluster, without SeekHead, Cues and Void, the Segment's size left open, then whole clusters; open-sized clusters, as browsers record them, found by scanning for the Cluster ID followed by a Timecode) and plain ADTS AAC (`analyzeAdtsInPieces`, one frame of overlap). A decoder starting mid-stream may lose or add a little at a piece's start, so each piece is placed by the file's own timestamps (`makeAlignedAnalyzer`: its end lands where the granule, cluster timecode, frame count or FLAC sample number says; short is padded with silence at the start, long is trimmed from the start), decoded at the file's own rate (Matroska at 48 kHz). All match decoding the whole file (tests/morepieces.js, including a WebM rewritten to open-sized clusters). Everything else (1.4.116: Apple Lossless where it plays, FLAC in Ogg, MP2, AC3, CAF, AMR…) goes through the converter when it's too long to decode whole, when reading it in pieces failed, or when it plays but won't decode here (`analyzeWithConverter`: ffmpeg decodes two minutes at a time, 45 s on a phone, with `-ss`/`-t` into 48 kHz 16-bit samples, read in place by WORKERFS, measured like any piece and placed by time; about 4 s per 5 minutes of audio on a computer). Used by import (`analyzeAudio`), Check library, the background loudness and stand-in repair. It steps aside (null, stand-in kept, the background repair comes back) while a conversion holds the converter, and does nothing without the converter on the device (normally fetched quietly at setup). tests/convpieces.js. Other formats past the budget get a stand-in waveform and no loudness, marked with the budget of the device that tried (`loudness.tooLong`, in MB); a device with a bigger budget (a computer) tries again, and the result reaches the others through sync. Budgets: 2000 MB on a computer reporting 8 GB, otherwise 1000 MB (about 45 minutes of stereo). Splitting a WAV or MP3 copies bytes instead (1.4.079); other formats go through the converter (1.4.086), and only decode whole on a device without it. On phones and tablets MP3/WAV always go in pieces (1 MB pieces for MP3 there). The first piece starts after an MP3's Xing/Info header frame (`mp3AudioStart`): with that and smaller pieces, an iPad that had crashed on four 2-hour MP3s analyzed each in about a minute (1.3.042, 19 Oct 2026). A background analysis that gets the page closed is remembered (`guardedAnalysis`, localStorage `37player.analyzing`) and that track is skipped by that version (`analysisCrashed` = version). The server's `list` reports stand-in waveforms (`flatPeaks`, exactly 3601 bytes) so a device with the real one replaces it. Waveforms travel separately from the library document (720 numbers a track would make every save megabytes): each is a small file on the server named after its audio version, sent with the audio and fetched with it. A flat stand-in is never sent. A device with a stand-in (`repairStandInPeaks`, once per track via the local `peaksTried`) first asks the server, else makes it and sends it with `replace=1`, the one case the server overwrites a file. Loudness is in the library document (the audio group), so it syncs directly.
- **Long work freezes the page:** decoding and loudness loops yield to the page (`yieldToPage`). A 90-minute track used to freeze the page for 9 s.

## Tried and abandoned (don't go back)

- **Server libraries** (ready-made collections to download, from `libraries/` on the site, with Settings → Remote for their address): removed in 1.4.006. Publicly hosting recordings isn't something Gen Rinzin can do; shared libraries (joined by code, not public) replace it, and Import / Export points to Settings → Shared library instead.

- **Screen off:** filling only the gap between tracks with silence didn't stop the drop-out. Routing all playback through Web Audio didn't either: the phone also paused tracks itself.
- **Wi-Fi-only syncing:** removed. Devices that quietly stayed out of date were worse than the data use.
- **Phone columns trading width with their neighbour** (1.4.053): a pair's total stayed fixed and the line to their left ate into it, so columns 3 and 4 often fit in less than the screen. On a phone each line sizes one column.
- **Merging two people's reordering of the same playlist:** that's where automatic merges go wrong. Keep both copies instead.
- **Master/follower roles for sync:** a joined device can edit, and can have things of its own.
- **Google Drive via OAuth as the *only* storage:** Google Cloud setup, sign-in tied to one site, and uncertain sharing across accounts. It comes back as one storage among several, per library (see Open / later).
- **A localhost helper for backups:** too much to install. Backups are automatic in Chrome/Edge and manual zips elsewhere.

- **File formats and converting** (talked through 20 Oct 2026; keeping unplayable files done in 1.3.048, converting them in 1.3.049, above):
  - **Principle:** keep everything, and let a capable device fix it. A file only needs converting once, anywhere: the result syncs to every device. Works the same with the droplet, Google Drive or no sync at all.
  - **Converter:** ffmpeg.wasm (the community build of ffmpeg for browsers), hosted on 37player.com, fetched by every device in the background and kept locally, so it works offline (phones and iPads turned out to be as capable as computers: see the measurements below). Decodes what browsers can't (ALAC, WMA, compressed AIFF), encodes MP3 and AAC on any browser including Linux Chrome and Firefox, faster than real time, reading big files in place (WORKERFS). Still to do: our own audio-only LGPL build, smaller than the standard 31 MB one.
  - **Measured 20 Oct 2026** with tests/convert/ (ffmpeg.wasm 0.12.10, standard build): MP3 192k at 40–46× real time on the T470 (Firefox), 75–79× on the iPad (Safari 26), 58–62× on an Android phone (Firefox); a 2-hour recording in 1½–2½ minutes. AAC 2–4× slower than MP3 (a 2-hour mono talk took 9½ minutes on the T470). Converter memory 32–55 MB whatever the file's length (it reads the input in place); the finished file is held until stored. So phones and iPads are capable converting devices too: no need to keep the converter to computers. Formats add no gap (0 ms on every device).
  - **Gapless playback is the player, not the formats:** 37 Player gives its one `<audio>` element the next file when a track ends, so there's always a short break between tracks, whatever the format; scheduling the next file sample-accurately (Web Audio) was seamless on every device. Not wanted for now: a month of use never ran into it, since sessions have silences and stops between items.

  - **Google Drive with several accounts** (talked through 29 Oct 2026). Today's way, one account on every device, is the **Simple Google Drive setup** (Gen Rinzin's name): for a Center, an account made for it (`sound@…`). A token is bound to the account chosen at sign-in, not to the browser's default Google account, so devices don't drift to someone's personal account; only a re-sign-in could, which 1.4.124 guards. With each person's own account: (1) `drive.file` grants are per account, so B can't see A's folder through Drive sharing alone: B picks it once in Google's Picker; (2) files B uploads into a folder in A's My Drive are owned by B and use B's storage, while in a **shared drive** they belong to the drive (Workspace for Nonprofits' pooled storage) and leaving people are simply removed from it. So the plan is shared drives + the Picker. What a picked folder grants (its contents? folders others made inside it?) is the undocumented part: **`gdrive-picker-test.html`** (29 Oct 2026; removed after the test, with tests/pickertest.js; in git history if ever wanted) signs in through token.php, opens the Picker (Picker API key + project number as App ID), and reports whether the folder, files put there by hand, and another account's run are seen, read and written, whether access lasts past a new access token, and whose storage new files use. Run it with two accounts on a shared drive before building. **Result (30 Oct 2026, Firefox, two personal accounts, a My Drive folder shared as Editor): it doesn't work.** Picking a folder gives access to that folder only: the app can create things in it, but sees none of the four files put there by hand, nor the folder and note.txt another account made through 37 Player itself (`drive.file` grants are per user, even for the app's own files). A shared library's files arrive all the time, so picking each one is no answer. Also, the Picker needs Google's third-party cookies: in Firefox it stayed blank until tracking protection was turned off for the site (Safari is likely similar). So with `drive.file`, a Drive library is one account on every device (the Simple Google Drive setup). Several accounts would need the full `drive` scope, which is restricted (a paid yearly security assessment): not worth it. People wanting their own accounts can use the droplet (join codes) or, later, pCloud/Dropbox.
