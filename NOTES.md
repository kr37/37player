# 37 Player: notes

The big picture as of 28 October 2026 (version 1.4.097). Commit messages hold the detail of each change. This file says how the whole thing works and why it is the way it is. Update it when a decision changes.

## What it is

A playlist player for live sessions at Kadampa centers: chanting, prayers, mandala offerings, teachings, with silences and stops between them. It's built for an operator who needs the right audio, in the right order, every time, often on an old computer or an iPad. It came out of IKRC's old and new Macs being unable to share a Music.app library, and Music.app becoming hard for non-technical people to use.

- One self-contained HTML file, `37-player.html`, running as a PWA. It's offline-capable, and the whole library (audio included) lives in the browser's IndexedDB.
- Users so far: Gen Rinzin, two friends, and Samudrabadra (Fort Myers). Prospective: KMC Texas (three rooms wanting one shared library) and IKRC (Macs and an iPad). Phones are a "handy sometimes" platform, not the main target.

## Architecture in brief

- **IndexedDB `temple-sound-library`.** Never rename it, or every user loses their library. Stores: `state`, `audio`, `artwork`. Audio and artwork are keyed by track ID; IDs never change.
- **Several libraries on one device** (1.4.001; Settings → Switch libraries, and the name in the top bar once there's more than one). Each library is its own database: the first is `temple-sound-library` (id `main`), the others `temple-sound-library~<id>`. The list is in localStorage `37player.libraries` (names, sizes, the last one chosen, ids of deleted ones), and each database also holds its own name (state record `libraryInfo`) so a lost list is rebuilt from `indexedDB.databases()` (`rediscoverLibraries`).
  - **Switching reloads the page** into the other library (`switchLibrary`), so nothing in memory carries over. Which library a window has open is per window (sessionStorage `37player.library`); two windows can have two libraries open.
  - **Per library:** everything in its database (library, view settings, session, backup record and folder, `sharedBase`, `sharedPending`, `sharedSeen`), and the channels, locks and localStorage keys that concern its contents: `libScoped()` adds `~<id>` (`37player-sync`, the sync, transfer, backup, tag-snapshot, mp4-repair and standardize locks, `37player.analyzing`, `37player.sharedLog`). The first library keeps the old names, so an older window still agrees with a newer one.
  - **Per device:** `DEVICE_SETTING_KEYS` (language, display, screen-off playback, the default device name, server addresses) in localStorage `37player.device`, laid over each library's settings on load and saved with every save; a `storage` event brings another window's change in before this window can save the old value back. The converter stays in the first library's database whichever is open (`mainStateGet/Put/Delete`). Device-wide channels and locks: `37player-playing`, `37player-version`, `37player-convert`, `37player-converter-fetch`, and `37player-libraries` (the list changed; a library was deleted).
  - **Only the open library syncs.** A new library starts empty (the starter prayer is only for the first). New library → Join a shared library joins at once after the reload (sessionStorage `37player.pendingJoin`) and takes the shared library's name. Joining from a library that already has tracks offers a new library first, since combining would put them in front of everyone.
  - **Deleting** is for libraries that aren't open: their database is deleted (the first library's is emptied instead, as it holds the converter). Windows on it are told, close it at once, and reload into another.
- **State is split** into the library (`library`, `tree`, `rev`) and the view (settings, session). The library is written only when its hash changes, and only if no other window has written since (`idbWriteLibraryIfCurrent`). A BroadcastChannel keeps other windows live.
- **Old windows:** two windows on one computer share one library, so a window left open on an old version syncs by old rules (a 1.3.021 window and a 1.3.045 one re-saved the library every 3 minutes all night). Each window announces its version on BroadcastChannel `37player-version`; one that hears of a newer version stops syncing and asks to be reloaded (1.3.047). Devices also strip local-only fields (`SYNC_LOCAL_TRACK_FIELDS`) from the shared library as they receive it (1.3.046).
- **Rule for all code:** `root.library` and `root.tree` can be replaced at any moment by another window or a sync. Hold IDs, never long-lived object references.
- **`sw.js`** can't be inlined (a spec restriction). It caches only the app page and `help.json`, network-first, and skips Range requests.
- **Help** is Markdown in `help/NNN Title.md`. It's embedded into the HTML because a `file://` copy can't fetch `help.json`. It's English only, by design.
- **The UI** is translated into 9 languages (en, es, fr, pt, de, zh, vi, el, it). Every new string goes into all nine.

## Playback model

- **Highlighted vs. queued.** "Highlighted" (`selectedItemId`) is UI only. "Queued or playing" (`currentItemId`) changes only through `activateItem()`. A single click highlights; a double-click or Enter plays from the start.
- **Each step.** The next item is looked up fresh when an item ends, so edits made mid-session take effect. Deleting the playing entry lets it finish.
- **Silences and stops.** Silences tick on their own clock. Stops wait for a click.
- **Only the latest press counts.** If a track's audio must be fetched first (shared library), a press that's still waiting is dropped when another is made. Playback never starts by itself minutes later.
- **Loudness.** "Even out loudness" and per-track +/- adjustments use `el.volume` when turning down. Turning up needs Web Audio (`createMediaElementSource` into a GainNode). Once an element is routed that way, it stays routed until reload.
- **No peak limit** (1.4.098, `trackLevel`; before, 1.4.059, evening out stopped at the loudest peak). Evening out and a track's own boost (✎, `volumeDb`) both go past the peak if that's what it takes; the details say how far past full volume the peaks go (`over`) and that turning the track down by as much avoids the distortion. Gen: loud enough on small speakers, with a warning, beats too quiet. Album by album is the default kind (`levelKind`, Settings lists it first). Album mode is one gain per album (its combined loudness), and each track's own Volume is added on top in either mode, and also with evening out off.

### Playing with the screen off (phones and iPads)

The hardest-won part. Found and fixed in October 2026 (1.3.022 to 1.3.028), using the playback log.

- **The problem:** on Android and iPadOS, a track that starts while the app is off screen (screen locked, or another app in front) plays for a couple of seconds, then goes silent. The player still reports "playing" and its time keeps running. The sound comes back when the app returns to the screen.
- **The fix:** while the app is off screen and the player is playing, a silent 10-second WAV loops on its own `<audio>` element (`silentKeepAlive`, `updateLoopHold`). The page never stops making sound in the phone's eyes. The same loop already carried silences along with the screen off.
- **Between items** (`playBridge`): the moment after one item ends and before the next is really playing counts as still playing. The loop stays on and the lock screen keeps saying "playing".
- **Stops** (`stopHold`): with "Keep the lock screen ready at stops" on (default), the silent loop runs through a stop, the lock screen shows the stop's name, and its play (or pause) button continues the session. Off saves battery; then a stop needs 37 Player itself.
- **Pauses off screen** (`pauseHold`, same setting, now "…at stops and pauses"): after a pause with the app off screen, the silent loop runs for up to 30 minutes so the lock screen's play still works. Without it an iPad put the page to sleep at once, and play gave no sound.
- **Lock-screen commands:** Media Session "play" only plays and "pause" only pauses. They used to toggle, so a stray "play" from the phone paused a playing track.
- **Phone pauses at a track's start:** if the phone pauses a track within 5 seconds of its start, with the app off screen and no press, it's restarted once. Later pauses (a phone call, unplugged headphones) are respected.
- **Diagnosis:** the **playback log** (Settings → Playback, `playLog()`) records track starts, the app leaving and returning to the screen, pauses the phone made, and a "still playing" line every minute. Keep it. Ask for it first whenever playback misbehaves on a device.

## Shared library sync (1.3.000 onward)

The full plan and history are in the project doc `shared-library-sync.md`. In short:

- **Server:** `sync.php` is plain PHP, with no framework or database. Libraries are joined by a secret code; the server stores only its hash.
- **Versions:** each library version is one JSON file, so history comes free. Saves are "only if still at version N" (`flock`); otherwise the server returns 409 and the app merges and retries. Audio and artwork are named `id.rev` and never overwritten.
- **Merging** is three-way: this device, the shared library, and the last-agreed base (IndexedDB `sharedBase`).
  - A change made in one place wins.
  - A track changed in both places merges field by field.
  - A playlist changed in both places: both are kept, with the device name added to the copy and a ⚠ mark.
  - Edited on one device, deleted on another: the edit wins.
  - A sibling merely moving is not an edit, so it never revives a deletion.
- **Engine:** the merge engine is the `SYNC-MERGE:BEGIN/END` block, pure functions with their own tests.
- **Transfers:**
  - Audio moves in the background, one window at a time: `navigator.locks`, with separate locks for down and up.
  - It waits while anything plays, because transfers made phones crackle. A track you press play on is still fetched at once, with one download per file at a time.
- **Keep syncing with the screen off** (phones and tablets): a setting that stays as set (`cfg.keepAwake`). While on, whenever there's something to send or receive and nothing is playing, a silent loop keeps the page awake, with progress on the lock screen. Playback stops it; it restarts the moment playback stops. The lock screen's pause holds it off until the app is next on screen or plays. When a track is paused part-way, the lock screen keeps the track ("Paused · Receiving 2 of 5"), and its play (or pause) button resumes the track.
- **Review changes:** a FreeFileSync-style overlay with arrows per row (send / take / skip). It holds back automatic syncing while open.
- **What's on this device** (1.4.007, `openSharedChoose`): the whole shared library as a tree with checkboxes and sizes; Albums open (▸) into their tracks, each ticked on its own with its size (1.4.068; ticked, a track comes with no playlist, which the selection already allowed: it's the set of folders, playlists and loose tracks); a track that comes with a ticked playlist shows ticked and locked, "comes with a playlist". Apply (`sharedApplySelection`) builds this device's document without what was unticked, marks what was ticked "take", and runs the review steps (`syncReviewRows`, `syncClassifyPartial`, `syncApplyDependencies`, `syncApplyReview`), so the engine is unchanged. On a full-sync device, unticking switches it to partial first, after asking. Settings → Shared library: **On this device: Everything / Only what I choose** replaces the Partial sync switch; with Only what I choose, **New playlists from other devices come here by themselves** (`cfg.autoNew`: before an ordinary sync, `sharedBringNewOnes` ticks what's new since last looked, by `sharedSeen`; turning it on marks everything current as seen). Opening What's on this device marks what's new as seen too (1.4.062: the count goes, the New marks stay for that visit), unless `cfg.autoNew` is on; before, only Apply did, and Apply needs a change, so "2 new" couldn't be dismissed. The New marks are bright green and beside the name (1.4.063): the small amber ones went unnoticed. Review changes is now only for Review mode; the "new" badge opens What's on this device.
- **Partial sync** (a "left sync", "Only what I choose" in the app):
  - **What it means, since this keeps being forgotten:** a LEFT JOIN with this device on the left. Everything on the device is also in the shared library; the shared library may hold more that this device doesn't. So once a partial-sync device is up to date, the shared library already has every one of its files, exactly as with a full-sync device. "Partial" only ever means the device holds less, never that the shared library does. Nothing on a partial device is device-only (that would be the old "On this device only" folder idea, never built).
  - Everything on the device syncs both ways.
  - New playlists from others arrive only when chosen in Review.
  - New tracks in playlists the device already holds arrive automatically.
  - Deleting offers three choices: Cancel / Remove from this device / Delete everywhere.
- **Missing tracks** are marked big and clear, saying where each one is coming from ("on its way from {device}" or "waiting for {device} to send it").
- **Upload size limit:** Apache 2.4.54+ refuses request bodies over 1 GiB by default (`LimitRequestBody`), answering 413. A 1.2 GB WAV hit it. Both sites' vhosts on the droplet have `LimitRequestBody 0` (confirmed 29 Oct 2026; see SYNC-SETUP.md). The app now stops resending a refused file until "Sync now" and says so in the status (1.3.045). A later improvement: send big files in pieces (resumable).
- **Mobile data:** treated like any other connection, because library integrity matters more. Only the join dialog warns about the size.

- **The icon** (1.4.122): the five-bar icon used since September, its bars exactly where they were (47 of 512 wide), on black, with a centre line edge to edge: the two left bars and their half of the line gold (#FFC233), the right ones blue (#3FA9FF), and the middle bar a red bar (#FF4040) of the same width from top to bottom. Red stays faint in a 16-px Firefox tab on Gen's KDE desktop whatever we tried (#E5332A, #FF1F1F; white in 1.4.121 showed better); he chose to keep red for now (1.4.122). At 16, 32 and 48 px everything is drawn on whole pixels (the red bar at least 2 px, gold and blue 1 px at 16 so the gaps stay, the centre line a pixel thicker than it would scale to): in a Firefox tab a scaled-down icon blended the thin red into the black until it all but vanished (red is dark to the eye; gold and blue survive). Two tab icons, 16 and 32, with `sizes`, so the browser needn't scale. Drawn in `art/37player-icon.svg` (the large design; small sizes are snapped by the script that renders them) and rendered: 512 and 192 in both manifests (the file and the copy inside the page), 180 for `apple-touch-icon`, 192 and a 16/32/48 .ico for the homepage. Tried and dropped the same day: a traced waveform picture (1.4.117, too faint in a tab), thin bars with a thin red line (1.4.118), and this design with a darker red and no centre line (1.4.119).

- **Re-encode target is AAC 192 kbps, 44.1 kHz, stereo, `.m4a`.** It re-encodes only uncompressed audio, codecs a browser can't play, and odd channel counts or sample rates. An ordinary 192k MP3 is never touched.
- **Files a browser can't play are kept, never thrown away** (1.3.048). Import stores the original and marks its track `needsConvert` with the format's name ("Windows Media Audio (WMA)", "Apple Lossless (ALAC)", "AIFF-C (ima4)"; `describeFormatProblem`), so playlists keep their place for it and nothing is lost. It's part of the audio group in sync, so every device shows it, and whichever device later converts the file clears it. Marked like a missing track (bold, with the reason under it; `trackCantPlay`, `markRowNotHere`), and Playing says how many in a playlist can't play. Library cleanup → Tracks that can't be played → **Check again** (`recheckStoredAudio`) re-reads stored files with today's decoders: an AIFF an older version left at 0:00 comes back as WAV. Only a playlist file posing as audio is still left out.
- **The converter is ffmpeg.wasm** (1.3.049): `scripts/get_ffmpeg.sh` puts ffmpeg-core.js and .wasm (0.12.10, about 31 MB) in the site's `ffmpeg/` (not in git; CORS via its .htaccess). A device downloads them once, when something first needs converting (or from Library cleanup → Converter), into IndexedDB's state store (record `converter`, kept when the library is replaced), so it works offline and in downloaded copies (which fetch from 37player.com). It runs in a worker built from inline source (`converterWorkerMain`), reading the input in place (WORKERFS). **Convert** (after an import, on Playing's banner, in Library cleanup) turns a track marked `needsConvert`, or a 0:00 track, into MP3 192k: channels kept, sample rate kept unless MP3 can't hold it, tags and picture carried, the library's details written in after (`applyConvertedAudio`). One queue, one window at a time (lock `37player-convert`); it waits while anything plays in any 37 Player window on the computer (each window says when it plays, BroadcastChannel `37player-playing`; `anyWindowPlaying`, also used by Standardize and background analysis), and a conversion under way when playback starts is dropped and done again after. Standardize's "Only when nothing is playing" switch turns this off for converting too.
- **Unplayable files are converted at import, without asking** (1.3.053). The converter is fetched quietly ahead of need (during setup while the language is chosen, and on any start where it's missing, once nothing plays; `fetchConverterWhenIdle`, `ensureConverter`). A conversion keeps the original in the audio store under `orig:<id>` (local to the device: not synced, not in backups; track field `original`, local), and at the end of the run "Keep the originals?" is asked once, with their size. A portable export takes a kept original; Library cleanup can discard them. Deleting a track's audio deletes its original (`idbDelete`).
- **The library's format settings** (1.3.054; Settings → File format, which replaces the old Standardize page and its background MediaRecorder queue, now stopped): one preferred format (presets standard / apple / small / lossless, or custom: MP3, AAC or FLAC, bitrate, rate, channels; FLAC asks "Not recommended" first) and when to convert: `untouched` (Don't touch my files: originals of unplayable files kept without asking), `reduce` (the default: WAV/AIFF as they come in), `rules`. Stored in `root.formatPolicy`, saved with the library, carried in the shared document as `doc.policy` (`syncMergePolicy`: one field, the side that changed it wins; a document from an older version leaves it as it was). Conversions as files come in are done by the importing device; the page shows what the settings would convert in the library now; converting them is in Library cleanup (1.4.017). A file waiting to be converted isn't uploaded (`convertSoon`, `convertQueue`): only the result is. Portable export can "Convert to the preferred format" (the Music.app case), leaving the library alone. Re-encoding leans the library to 44.1 kHz stereo (the lossy presets set both, 1.3.055: stereo costs nothing at a constant bitrate); MP3 is constant bitrate (`-abr 0`) so seeking is exact. Kept originals stay on the converting device (the question says so in a shared library). Video files: asked about, their sound taken out (AAC/MP3 copied as is, anything else to the preferred format), the video not kept.
- **A shared library is a joined device's backup** (1.4.004). The welcome asks first whether the device will share a library, with the join code right there; a device that joins gets no backup advice (a computer that can keep a folder is offered one, as optional). "Back up library" and the reminder on leaving Edit stay away while everything on the device is in the shared library (the button reads "In sync"; "Syncing…" meanwhile; tapped, its backup dialog opens with "Up to date"): `sharedCoversLibrary`, the library's fingerprint at the moment the shared library held all of it, audio included (`sharedSyncedFp` after a sync round, then `sharedNoteCovered` once the uploads finish; state record `sharedCovered`). Meanwhile, joined, two-way and online, nothing asks (`sharedAboutToCover`). A receive-only device is covered when it has changed nothing.
- **Who keeps backups** (`doc.keepers`, `root.backupKeepers`: device name → time): a device with an automatic backup folder notes its backups in the shared library, at most every 12 hours, since each note is a new version. Merged per device, the later time winning (`syncMergeKeepers`, in the engine). Shown on the button's tooltip, in Settings → Backups and Shared library: "Backed up by Gen's laptop, today". No roles: any device can be a keeper.
- **Restoring and shared libraries** (1.4.004). Restoring a backup on a joined device used to keep it joined while dropping `sharedBase`, so the next sync put back everything deleted since the backup, for everyone. Now a whole-library restore on a joined device offers **Get the current shared library** first (`rejoinSharedLibraryFresh`: empty this device, join again, Use the shared library), or leaves the shared library before restoring. A backup records which shared library it's from (`meta.sharedFrom`: name and server, never the code); restoring one where it isn't joined suggests joining instead.
- **The welcome fits the device and browser** (1.4.002, `setupEnvironment`). Chrome/Edge on a computer: the backup folder, nothing about other browsers or a local copy (the folder gets 37-player.html anyway). Firefox/Safari on a computer: "works best in Chrome or Edge", with Copy the address, before anything is added. - **What can be imported:** `AUDIO_EXTENSIONS` (everything browsers play, plus what the converter decodes: WMA, ALAC, AC-3/E-AC-3, DTS, WavPack, TTA, AU, VOC, W64, Speex, RealAudio, CAF, MP2 …; each checked 21 Oct 2026 to import and play) and `VIDEO_EXTENSIONS` (sound taken out). - **Tag edits must never need a re-encode, and must never silently destroy tag information.** Getting the right audio in the right order matters more than perfect metadata.
- **History** (1.4.084; Settings → Shared library and Backups → **History…**, `openSharedHistory`). Lists the versions the shared library keeps (sync.php's `op=history`; on Drive the state folder's files), newest first, grouped by day, with who saved each and what it changed. Each save now sends that (`sharedPostState(cfg, base, doc, prev, extra)`: headers `X-Saved-By` and `X-Change`, a compact `syncChangeSummary`: counts `ta/td/tc` tracks, `pa/pd/pc` playlists and `fa/fd/fc` folders added/deleted/changed with the first name of each (`pan`…), `oc` orders, `rs` the time a restore came from), only to a sync.php ≥ 1.4.084 (`X-Sync-Version`: across sites an older one would refuse the headers and every save) or Drive. sync.php keeps them beside each version as `state/000123.json` (`info_file`, removed with its version by cleanup); Drive as the state file's `appProperties` `by` and `w` (124 bytes per key and value: names shortened, then dropped, `driveHistoryProps`). Older versions show "Saved".
  - **Comparing:** restoring is a review in which "now" (the shared library's current version, after sending this device's changes) is both sides and the earlier version plays the shared library: `syncReviewRows(now, now, then)` gives one row per difference; `syncRestore(now, then, keys)` takes the chosen rows (`syncApplyDependencies` adds the tracks a restored playlist needs) and gives the new document, posted as a new version based on now's (a 409 or a newer version: rows recomputed, choices kept where the row is unchanged, `histRecompare`), then a sync brings it here. **What changed at this point**: `syncReviewRows(previous, previous, then)`, view only. Receive-only devices can look, not restore.
  - **Screen:** points down the side with ‹ › to step (radio buttons for the two views, per Gen: two-coloured toggle buttons are hard to read), rows with Keep now / Restore, playlist rows open to both versions side by side, items marked added/gone/changed. Tests: tests/engine/hist-test.js, tests/hist.js.
- **Settings → Shared library tidied** (1.4.084): Review changes before syncing, Receive updates only, Keep syncing with the screen off, the Sync log and the server's version folded into a closed **More** (`sharedMoreOpen` keeps it open across redraws). On this device stays as radio buttons.
- **Undo and redo** (1.4.084; ↶ ↷ beside Settings on Edit Playlists and Library, Ctrl/⌘-Z, Ctrl/⌘-Shift-Z, Ctrl-Y). Every library write (`doSaveState` → `undoNoteSaved`) compares the library with a starting point (`undoBase`, `undoDoc`: tracks without the audio, artwork and local fields, so background work never makes a step) and keeps the rows that differ, before and after, as a step (`undoStack`, up to 30, in state record `undo`, so they survive a reload); saves within 1.2 s join. What arrives from the shared library (`sharedApplyDoc`) or another window (`reloadLibraryFromStorage`) only moves the starting point (`undoRebase`). Undoing (`undoApply`) puts back only records still as the step left them (a later change from elsewhere stays, and the notice says so), keeps tracks a playlist still uses, and rebuilds the tree (`syncBuildDoc`). A deleted track's full record is kept in the step; its audio and artwork go to `undotrash:<time>:<id>` state records for a day (`deleteLibraryTracks` → `undoTrashPut`; purged hourly), so undoing a deletion brings the sound back; otherwise, in a shared library, it's fetched again. Artwork changes and conversions aren't undoable (artwork counts as audio detail). Find duplicates keeps its own Undo. ## Browser quirks and workarounds

- **Clear a file input's value only after copying its files.** Chromium 141 empties the input's FileList in place when its value is cleared. Copy with `Array.from()` first.
- **Playlist files report as audio.** `.m3u8` reports as `audio/x-mpegurl`, so audio is picked by extension, never by MIME type.
- **Safari:**
  - it clears a site's data after 7 days without use, unless the app is on the Home Screen or Dock;
  - it uses dynamic viewport (`dvh`) heights;
  - the window's scroll position needs resetting, except while typing.
- **iPad touch:**
  - no hover, so row icons appear on selection;
  - drag and drop is synthesized from touch for the folder tree;
  - native `draggable` is turned off on coarse pointers.
- **Folder access:** `showDirectoryPicker` works only in Chrome and Edge on desktop. Brave needs `brave://flags` → File System Access. iOS Chrome is WebKit, so it has no folder access either.
- **Codecs:**
  - ALAC and WMA play in no browser, so they're converted with the scripts in `scripts/`.
  - What MediaRecorder writes as "AAC" varies by browser. Some write Opus, which `findMp4AudioCodecFourcc` catches.
- **Long recordings and memory:** decoding a whole file holds it all as raw samples (a 2-hour stereo teaching is about 2.5 GB), which crashed a phone's tab ("Aw, Snap!") and made a laptop give up with a flat stand-in waveform. Past a per-device budget, MP3s are decoded about 3 minutes at a time, cut at frame boundaries (`analyzeMp3InPieces`), and WAVs are read a few MB at a time with no decoder (`analyzeWavInPieces`); both feed `makePieceAnalyzer` / `makeLoudnessMeter`. Since 1.4.108, AAC in an .m4a/.mp4 too (`analyzeM4aInPieces`; Gen's long Zoom recordings had stand-ins and no loudness): `m4aAacFrames` reads the sample table (stsz, stsc, stco/co64) and the AudioSpecificConfig (esds), and about 3 minutes of frames at a time (45 s on a phone) each get a 7-byte ADTS header and go to `decodeAudioData` as plain .aac. Each piece after the first starts one frame early and drops that frame's sound (AAC overlaps frames); the edit list's lead-in (`elst` media_time) and its duration are honoured, so the result matches decoding the whole file exactly (tests/m4apieces.js). Apple Lossless and other non-AAC throw, keeping the stand-in; on phones an .m4a still decodes whole when it fits (it may be Apple Lossless, which Safari decodes but can't be cut this way). Since 1.4.114 also FLAC (`analyzeFlacInPieces`: a minimal header from STREAMINFO, total and MD5 left unknown, then frames; cut where a frame starts, found by sync code and header CRC-8), Ogg Vorbis and Opus (`analyzeOggInPieces`: the header pages, then whole pages starting with one that doesn't continue a packet), WebM/Matroska (`analyzeMkvInPieces`: EBML header and the Segment's children up to the first Cluster, without SeekHead, Cues and Void, the Segment's size left open, then whole clusters; open-sized clusters, as browsers record them, found by scanning for the Cluster ID followed by a Timecode) and plain ADTS AAC (`analyzeAdtsInPieces`, one frame of overlap). A decoder starting mid-stream may lose or add a little at a piece's start, so each piece is placed by the file's own timestamps (`makeAlignedAnalyzer`: its end lands where the granule, cluster timecode, frame count or FLAC sample number says; short is padded with silence at the start, long is trimmed from the start), decoded at the file's own rate (Matroska at 48 kHz). All match decoding the whole file (tests/morepieces.js, including a WebM rewritten to open-sized clusters). Everything else (1.4.116: Apple Lossless where it plays, FLAC in Ogg, MP2, AC3, CAF, AMR…) goes through the converter when it's too long to decode whole, when reading it in pieces failed, or when it plays but won't decode here (`analyzeWithConverter`: ffmpeg decodes two minutes at a time, 45 s on a phone, with `-ss`/`-t` into 48 kHz 16-bit samples, read in place by WORKERFS, measured like any piece and placed by time; about 4 s per 5 minutes of audio on a computer). Used by import (`analyzeAudio`), Check library, the background loudness and stand-in repair. It steps aside (null, stand-in kept, the background repair comes back) while a conversion holds the converter, and does nothing without the converter on the device (normally fetched quietly at setup). tests/convpieces.js. Other formats past the budget get a stand-in waveform and no loudness, marked with the budget of the device that tried (`loudness.tooLong`, in MB); a device with a bigger budget (a computer) tries again, and the result reaches the others through sync. Budgets: 2000 MB on a computer reporting 8 GB, otherwise 1000 MB (about 45 minutes of stereo). Splitting a WAV or MP3 copies bytes instead (1.4.079); other formats go through the converter (1.4.086), and only decode whole on a device without it. On phones and tablets MP3/WAV always go in pieces (1 MB pieces for MP3 there). The first piece starts after an MP3's Xing/Info header frame (`mp3AudioStart`): with that and smaller pieces, an iPad that had crashed on four 2-hour MP3s analyzed each in about a minute (1.3.042, 19 Oct 2026). A background analysis that gets the page closed is remembered (`guardedAnalysis`, localStorage `37player.analyzing`) and that track is skipped by that version (`analysisCrashed` = version). The server's `list` reports stand-in waveforms (`flatPeaks`, exactly 3601 bytes) so a device with the real one replaces it. Waveforms travel separately from the library document (720 numbers a track would make every save megabytes): each is a small file on the server named after its audio version, sent with the audio and fetched with it. A flat stand-in is never sent. A device with a stand-in (`repairStandInPeaks`, once per track via the local `peaksTried`) first asks the server, else makes it and sends it with `replace=1`, the one case the server overwrites a file. Loudness is in the library document (the audio group), so it syncs directly.
- **Long work freezes the page:** decoding and loudness loops yield to the page (`yieldToPage`). A 90-minute track used to freeze the page for 9 s.

## Tried and abandoned (don't go back)

- **Server libraries** (ready-made collections to download, from `libraries/` on the site, with Settings → Remote for their address): removed in 1.4.006. Publicly hosting recordings isn't something Gen can do; shared libraries (joined by code, not public) replace it, and Import / Export points to Settings → Shared library instead.

- **Screen off:** filling only the gap between tracks with silence didn't stop the drop-out. Routing all playback through Web Audio didn't either: the phone also paused tracks itself.
- **Wi-Fi-only syncing:** removed. Devices that quietly stayed out of date were worse than the data use.
- **Phone columns trading width with their neighbour** (1.4.053): a pair's total stayed fixed and the line to their left ate into it, so columns 3 and 4 often fit in less than the screen. On a phone each line sizes one column.
- **Merging two people's reordering of the same playlist:** that's where automatic merges go wrong. Keep both copies instead.
- **Master/follower roles for sync:** a joined device can edit, and can have things of its own.
- **Google Drive via OAuth as the *only* storage:** Google Cloud setup, sign-in tied to one site, and uncertain sharing across accounts. It comes back as one storage among several, per library (see Open / later).
- **A localhost helper for backups:** too much to install. Backups are automatic in Chrome/Edge and manual zips elsewhere.

Today's way, one account on every device, is the **Simple Google Drive setup** (Gen's name): for a Center, an account made for it (`sound@…`). A token is bound to the account chosen at sign-in, not to the browser's default Google account, so devices don't drift to someone's personal account; only a re-sign-in could, which 1.4.124 guards. With each person's own account: (1) `drive.file` grants are per account, so B can't see A's folder through Drive sharing alone: B picks it once in Google's Picker; (2) files B uploads into a folder in A's My Drive are owned by B and use B's storage, while in a **shared drive** they belong to the drive (Workspace for Nonprofits' pooled storage) and leaving people are simply removed from it.
